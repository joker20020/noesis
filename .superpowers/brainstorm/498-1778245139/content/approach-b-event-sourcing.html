方案 B：事件溯源 Agent 系统 — 核心架构

一切皆为事件。状态是可推导的，历史是可回放的，进化是可追溯的。

核心理念

传统架构（含 GenericAgent）的 agent 是 状态驱动 的：文件内容改变、记忆写入、工具执行结果覆盖旧状态。一旦操作完成，为什么这么做、中间怎么想的、有没有其他选择 全部丢失。

事件溯源逆转这个逻辑：不存储最终状态，而是存储导致状态变化的事件序列。状态只是事件流的投影。

核心概念：Write Side vs Read Side (CQRS)

Write Side (命令端) Read Side (查询端)
只做一件事：产生事件

Agent 认知循环 → 调用工具 → 工具执行 → 产生事件

不做任何查询，不构建任何视图。只验证规则，然后追加事件到 Event Store。 		只做一件事：消费事件构建投影

内存投影：从事件流重建当前记忆 L0-L4
Neo4j 投影：实体+关系实时同步
UI 投影：WebSocket 推送时间线更新

相对于 GA 的关键改进

维度 GenericAgent (文件记忆) 方案 B (事件溯源)
可追溯性 L4 保存对话归档，但缺乏结构化时序索引 每个决策的完整因果链可精确回溯
进化透明度 技能从 SOP→代码，中间推理不可见 SkillEvolved 事件记录每次进化的 diff 和触发原因
记忆一致性 直接写入文件，可能冲突或不一致 事件是唯一真相源，记忆投影始终一致
学习价值 只能看到结果，看不到过程 时间线回放让你观察 agent 如何思考，这对学 OSINT/社工极有价值
实验能力 难以做 A/B 对比 从同一快照分叉不同策略，对比结果

方案 B 的技术代价

需要注意的问题

  • Event Store 膨胀：一个任务可能产生 50-200 个事件，需快照机制压缩
  • 投影延迟：读侧从事件重建状态有计算开销，需缓存策略
  • 开发复杂度：团队需要理解 CQRS 和事件建模思维
  • 事件版本演进：事件 schema 变化时需处理向后兼容
